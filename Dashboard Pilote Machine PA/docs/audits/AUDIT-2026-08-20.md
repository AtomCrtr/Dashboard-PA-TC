# Mise à jour et audit global — Dashboard Pilote Machine PA

**Date de l’audit :** 20/08/2026

**Périmètre :** code Apps Script, interface Pilotage/Revue MFT, règles de calcul et quatre échantillons de données locaux.

**Statut :** demandes traitées dans le code ; redéploiement Apps Script et reconstruction MES requis pour les voir dans l’application publiée.

## Résumé exécutif

Les libellés du dashboard ne permettaient pas de comprendre suffisamment les indicateurs. Le calcul était généralement cohérent avec le code, mais plusieurs informations essentielles restaient invisibles : dénominateur de la couverture master, formule de l’indice d’impact, champ utilisé pour classer les défauts, raison de l’absence de MES dans les familles et limite du taux pour 1 000 perçages.

Les corrections rendent maintenant ces éléments explicites et ajoutent un audit qualité dynamique selon les filtres. La Revue MFT affiche la famille associée à chaque IMMO et alimente directement une table MFT officielle normalisée, indépendante des feuilles copiées.

Les anomalies de code les plus importantes corrigées sont :

1. des valeurs `DOTATION`, `A ENQUETER` ou `METHODES` pouvaient être indexées comme des IMMO du master ;
2. un IMMO TC cité dans un commentaire MES PA pouvait être rapproché ;
3. le bouton de clôture MFT envoyait une mise à jour partielle que le serveur refusait ;
4. la tendance hebdomadaire ignorait les dates choisies dans les filtres ;
5. le nombre d’anomalies affiché comptait les groupes de contrôle et non leurs occurrences ;
6. un temps MES fourni en CSV sous la forme `0-01:30:00` était converti en zéro.

## Réponses aux demandes — Revue MFT

### IMMO prioritaire sans famille

Corrigé. Chaque IMMO agrégé transporte maintenant sa famille master. La liste affiche `IMMO · famille`, le détail production/NC/MES, le nombre d’impacts et le nombre de points d’impact. Un clic préremplit à la fois l’IMMO, la famille et un constat compréhensible.

### Signification de « impacts sur les 3 dernières semaines »

La période correspond exactement aux **21 jours calendaires**, date de début et date de fin incluses. Ce n’est ni une moyenne, ni une évolution par rapport aux trois semaines précédentes.

Un **impact machine** est une quantité affectée à un IMMO. Une déclaration concernant plusieurs IMMO produit un impact pour chaque machine. Le nombre de déclarations distinctes reste séparé dans les KPI.

L’**indice d’impact** est un score de priorité :

`quantité × poids de la source`

Avec les paramètres par défaut :

`aléas production × 1 + non-conformités × 5 + aléas MES × 1`

Ce score est exprimé en points. Il ne représente ni des euros, ni une gravité certifiée, ni un pourcentage. Un lexique est maintenant visible dans la Revue MFT et les pondérations réellement présentes dans `FAITS_IMMO` sont renvoyées par le serveur.

### Double saisie entre préparation et plan officiel

Corrigé par la création d’un référentiel officiel normalisé dans le classeur « Plan actions aléas machines PA » :

- `MFT_ACTIONS_OFFICIEL` contient une ligne stable par action et reprend les champs métier du fichier historique : référence, demandeur, date, constat, action décidée, responsables, échéance initiale, statut, priorité et identité machine ;
- `MFT_SUIVI_OFFICIEL` contient une ligne horodatée par commentaire, changement de statut ou nouvelle date promise ;
- `MFT_REUNIONS_OFFICIEL` conserve les dates, participants et compteurs des réunions ;
- le dernier ancien onglet daté et l’éventuelle table locale `ACTIONS_MFT` sont migrés une seule fois, sans doublon ;
- après migration, le dashboard ne lit plus les onglets copiés et ne dépend plus de leur nom ou de leur mise en forme ;
- l’échéance d’origine est immuable ; une révision est tracée séparément comme nouvelle date promise.

La table officielle devient l’unique source de vérité. Les anciennes feuilles MFT peuvent rester dans le classeur comme archives, mais elles n’influencent plus l’application.

## Réponses aux demandes — Pilotage

### Couverture master à 81 %

La formule exacte est désormais affichée :

`quantité des impacts dont l’IMMO existe dans BDD_Master_amélio ÷ quantité de tous les impacts filtrés`

Le KPI montre maintenant le numérateur et le dénominateur, par exemple `X / Y impacts reliés au master`, ainsi que le nombre d’impacts ayant simplement un IMMO renseigné. Ces deux notions n’étaient auparavant pas distinguées dans le texte du KPI.

Le taux de 81 % observé dans l’application publiée ne peut pas être reproduit exactement avec le seul dépôt local, car le classeur central `FAITS_IMMO` courant n’est pas fourni. Sur les échantillons locaux complets et en exigeant un rattachement master PA, la simulation donne environ **87,3 %** ; sur les 21 derniers jours présents dans les échantillons, **12 impacts sur 13** sont reliés au master. La valeur de 81 % dépend donc des données et filtres du déploiement au moment de l’affichage. L’audit dynamique indique désormais quelle source produit les impacts non couverts.

**Diagnostic probable, confiance moyenne :** MES est la principale source de baisse, car l’export Qlik Sense ne fournit presque jamais d’identifiant machine exploitable en colonne et l’information est saisie librement dans `Commentaire initial`. Le panneau qualité permet maintenant de mesurer cette limite sur la période réellement affichée.

### Audit des données MES et de « Commentaire initial »

Constats vérifiés sur `exemple-export-mes-qlik.xlsx` :

| Mesure | Résultat |
|---|---:|
| Lignes exportées | 376 |
| Disruptions PA `UPA MEDU` conservées | 269 |
| Lignes exclues car autre objet | 107 |
| Temps perdu conservé | 154,68 h |
| Lignes avec temps perdu positif | 121 |
| Commentaires initiaux renseignés | 269 / 269 |
| `ID équipement` renseigné | 0 |
| `Matériels` renseigné | 0 |
| `Jig &Tools` renseigné | 3 |

Après nettoyage du master et limitation stricte au périmètre PA, la simulation du rapprochement donne :

| Méthode | Impacts |
|---|---:|
| IMMO lu dans une colonne existante de l’export | 2 |
| IMMO unique trouvé dans le commentaire | 73 |
| Plusieurs IMMO trouvés, à vérifier | 20 |
| Famille déduite du commentaire | 75 |
| Aucun IMMO/famille suffisamment fiable | 99 |

Au total, **96/269** impacts MES ont un IMMO PA proposé et **170/269** ont une famille master proposée. Ces résultats proviennent d’une indexation textuelle soumise au facteur humain ; ils ne constituent pas une validation métier automatique. Le dashboard affiche maintenant ces chiffres, la répartition des méthodes et les ambiguïtés. Les 269 lignes restent visibles dans le Top des défauts, même si elles ne peuvent pas toutes entrer dans un Pareto IMMO ou famille.

### Pareto des IMMO au-delà du top 10

Corrigé. Le graphique conserve le top 10 en première vue. Un bouton affiche ou masque tous les autres IMMO dans un tableau classé, avec rang, famille, production, NC, MES et total.

### Pareto des familles sans MES

Ce comportement est possible mais doit être expliqué : un impact MES n’entre dans le Pareto familles que si une famille du master a été trouvée. Les événements sans identité fiable restent dans l’analyse des défauts. Avec le nouveau rapprochement appliqué à l’échantillon, 170 impacts MES sur 269 ont une famille ; après redéploiement, il faut lancer **Reconstruire l’historique MES** pour recalculer les archives.

Le sous-titre du graphique affiche maintenant `MES : X / Y` pour la période filtrée. Si X vaut zéro, l’absence de barre MES est normale et directement justifiée.

### Impacts / 1 000 perçages

Ce n’est **pas un pourcentage**. La formule est :

`impacts de la famille × 1 000 ÷ nombre de perçages de la famille`

Limite importante : le TCD de perçages fourni est cumulatif et ne contient aucune date, alors que le numérateur suit la période du dashboard. Le résultat donne un ordre de grandeur mais pas un vrai taux limité aux trois dernières semaines. Pour obtenir un indicateur strictement comparable, le volume de perçages doit être fourni par semaine ou par date.

### Top des défauts machines

- axe Y : `Aléa` pour la production, `Typologie défaut` pour les NC et `Attribut` pour MES ; `Catégorie` sert uniquement de repli si le défaut est vide ;
- axe X : indice d’impact pondéré en points ;
- classement : ordre décroissant de cet indice.

### Temps perdu MES par défaut

- axe Y : `Attribut` MES ;
- axe X : somme de `Temps perdu`, en heures ;
- classement : heures perdues décroissantes.

Le parseur accepte maintenant aussi les durées textuelles CSV `J-HH:MM:SS` et `HH:MM:SS`.

## Améliorations recommandées pour la gestion des données

### Priorité 1 — Encadrer le rapprochement MES sans modifier Qlik Sense

L’ajout d’un champ IMMO dans l’export MES n’est pas réalisable. Il faut donc conserver `Commentaire initial` comme donnée source, assumer son facteur humain et sécuriser l’indexation autour de ce texte :

- distinguer clairement « proposé automatiquement », « validé », « rejeté » et « à vérifier » ;
- créer une table de correspondance approuvée pour les formulations récurrentes et corrections déjà validées ;
- proposer une file de revue des commentaires ambigus, sans correction automatique silencieuse ;
- mémoriser le validateur, la date et le motif de chaque décision ;
- suivre séparément le taux d’IMMO proposés et le taux d’IMMO réellement validés.

Si les pratiques opérateur peuvent évoluer sans modifier Qlik Sense, un aide-mémoire de saisie peut recommander de citer l’IMMO de façon lisible. Cela reste une aide et non une contrainte technique fiable.

### Priorité 2 — Historiser l’activité de perçage

Remplacer le TCD cumulatif par une table normalisée :

`DATE_SEMAINE | FAMILLE | POSTE | NB_PERCAGES | SOURCE | DATE_CHARGEMENT`

Le taux pour 1 000 pourra alors utiliser exactement le même intervalle que les impacts, être comparé d’une MFT à l’autre et recevoir un indicateur de complétude.

### Priorité 3 — Formaliser un contrat de données

Pour chaque source, définir les colonnes obligatoires, types, valeurs autorisées, unité et règle de dédoublonnage. Exemple MES : date valide, `Objet = UPA MEDU`, `EAP = PA A350 STR`, durée en heures, `Disruption ID` stable, commentaire initial conservé sans altération et méthode de rapprochement tracée.

Ajouter des seuils visibles :

- couverture master globale cible ≥ 98 % ;
- 100 % des rapprochements MES ambigus revus ou explicitement laissés en attente ;
- commentaires MES présents ≥ 98 % ;
- durée renseignée selon la règle métier à définir ;
- aucune valeur master invalide ;
- aucun rapprochement ambigu non traité depuis plus d’une MFT.

### Priorité 4 — Normaliser le plan MFT — réalisé dans cette mise à jour

Le plan repose désormais sur `MFT_ACTIONS_OFFICIEL`, `MFT_SUIVI_OFFICIEL` et `MFT_REUNIONS_OFFICIEL`. Les champs et règles suivent le fichier « Plan actions aléas machines PA 2026 », notamment les statuts, les niveaux de priorité et la conservation de l’échéance d’origine. Les feuilles de réunion deviennent des archives ou des vues de restitution.

### Priorité 5 — Industrialiser les contrôles et les tests

- conserver les tests locaux ajoutés dans `tests/run-tests.js` ;
- ajouter un petit jeu de données synthétique versionné pour tester une consolidation complète ;
- enregistrer à chaque actualisation un snapshot des KPI qualité dans une feuille `HISTORIQUE_QUALITE` ;
- déclencher une alerte si couverture, volume ou temps perdu varie brutalement ;
- ne jamais corriger automatiquement une correspondance ambiguë sans validation et table de correspondance approuvée.

### Priorité 6 — Performance et traçabilité

Apps Script reste adapté au volume actuel. Avant 100 000 à 200 000 faits, prévoir : lectures/écritures par lots, cache des index master, journal d’exécution structuré et archivage des erreurs. Au-delà, déplacer les faits vers un stockage analytique tout en conservant Sheets comme interface métier si nécessaire.

## Vérification réalisée

Le test local valide :

- la syntaxe des quatre fichiers Apps Script et du JavaScript HTML ;
- l’exclusion des faux IMMO ;
- le respect du périmètre PA lors du rapprochement MES ;
- le classement complet au-delà du top 10 ;
- les pourcentages de l’audit qualité ;
- le parsing des durées MES ;
- la compatibilité de migration avec l’ancien plan officiel ;
- les statuts MFT normalisés et le calcul automatique du retard ;
- la clôture MFT par mise à jour partielle sans perte des champs ni modification de l’échéance initiale.

Commande : `npm test`.

## Mise en production requise

1. Copier les fichiers `apps-script` mis à jour dans le projet Apps Script.
2. Vérifier que le propriétaire du déploiement a les droits d’écriture sur le plan officiel.
3. Exécuter `initialiserApplication`, ou le menu **Initialiser / migrer la table MFT officielle**, pour créer les trois tables et migrer les actions existantes.
4. Exécuter **Reconstruire l’historique MES** afin d’appliquer les nouvelles règles aux archives.
5. Contrôler `CONTROLES`, en priorité les IMMO master invalides et rapprochements MES à vérifier.
6. Créer une nouvelle version du déploiement web et effectuer un test avec une action MFT de démonstration.

## Limites de l’audit

Le dépôt local ne contient ni le classeur central Google Sheets `BDD Pilotage Machine`, ni son `FAITS_IMMO` courant, ni un accès au déploiement web. Les calculs et données sources locales sont audités avec une confiance élevée ; l’explication chiffrée exacte du 81 % affiché dans l’instance actuelle reste dépendante de son contenu et de ses filtres au moment de l’observation.
